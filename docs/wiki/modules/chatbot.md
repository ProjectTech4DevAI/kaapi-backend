# Module: Chatbot

A project has many chatbots; each chatbot's behaviour is a React Flow graph (nodes + edges JSON) edited in the UI and versioned with draft/publish, so editing never breaks running conversations. Agent nodes carry their own `prompt` and saved Kaapi config (`config_id` + `config_version`, pinned at publish); only Anthropic text completion configs are supported, using the **project's own Anthropic credentials** (no platform fallback). Conversations are server-side sessions pinned to the live flow version and an active node; turns run on Celery and reply via webhook. The runtime executes three agent node types: `onboarding` ("Beneficiary Info Extractor" over a two-node LangGraph: the node prompt defines the goal, fields to collect and rules; each turn extracts the fields given so far and then replies), `rag` (answers questions from the config's knowledge bases — OpenAI vector stores searched with the project's OpenAI credentials — over a tool-calling LangGraph; the node prompt is the goal and decides scope) and `coordinator` (routes each message to an onboarding or rag node by edge intent). No deep-dive doc yet.

All paths relative to `backend/app/`.

## Routes (`/chatbots`, all require project scope and the `CHATBOT` feature flag)
- `api/routes/chatbot/__init__.py` mounts session routes first so literal `/sessions/...` paths are matched before `/{chatbot_id}/...`. `require_feature(FeatureFlag.CHATBOT)` sits on the router → 403 when off. Migration `088` also adds the enum value — no rows are seeded, so the flag is off until a superuser creates it per project via `POST /feature-flags` (`enabled: true`).
- `api/routes/chatbot/chatbot.py`
  - `POST /chatbots` {name} → 201 `ChatbotPublic`
  - `GET /chatbots?skip=&limit=` → the project's non-deleted chatbots, newest `updated_at` first
  - `GET /chatbots/{chatbot_id}`, `PATCH /chatbots/{chatbot_id}` {name} → 404 when unknown/deleted
  - `DELETE /chatbots/{chatbot_id}` → 200 `Message`; soft delete + deactivates the chatbot's active sessions in the same transaction
- `api/routes/chatbot/flow.py` (response `ChatbotFlowVersionPublic` {id, chatbot_id, version, is_live, nodes, edges, inserted_at, updated_at})
  - `GET /chatbots/{chatbot_id}/flow?version=` → that version; default the draft if one exists, else live; 404 if no versions
  - `PUT /chatbots/{chatbot_id}/flow` {nodes, edges} → first save creates v1 already live (strict publish validation + pin, 422 on failure); later saves upsert the draft (shape-only validation); 409 on a concurrent version insert
  - `POST /chatbots/{chatbot_id}/flow/publish` → 409 without a draft, 422 listing every strict-validation problem
- `api/routes/chatbot/session.py`
  - `POST /chatbots/{chatbot_id}/sessions` {contact_ref} → 201 {session_id, chatbot_id, flow_version, active_node_id}; 404 unknown/deleted chatbot; 409 no live flow or concurrent create
  - `GET /chatbots/sessions/latest?contact_ref=&chatbot_id=` → `ChatbotSessionSummary` (incl. `chatbot_name`, `flow_version`, `active_node_id`, the active node's `prompt`); `chatbot_id` omitted = newest across the project's non-deleted chatbots
  - `POST /chatbots/sessions/{session_id}/message` → stores the user message with `node_id = active_node_id`, enqueues the turn → 202; 409 if the session is inactive; 422 when `message` is omitted on a started session or on a `rag` active node (rag has no opening greeting)

## Tables (SQLModel, `models/chatbot.py`, migration `088`)
- `chatbot` (`Chatbot`) — `name`, org/project FKs (CASCADE), `deleted_at` soft delete (sessions reference it with RESTRICT).
- `chatbot_flow_version` (`ChatbotFlowVersion`) — `chatbot_id` (CASCADE), `version` (UNIQUE with chatbot_id, `uq_chatbot_flow_version_chatbot_version`), `nodes` / `edges` JSONB stored as the UI sent them (React Flow camelCase keys, extra UI keys round-trip), `is_live` with partial unique index `uq_chatbot_flow_version_live_chatbot` (`WHERE is_live`). The highest version is the draft when not live; live versions are immutable.
- `chatbot_session` (`ChatbotSession`) — `chatbot_id` (RESTRICT), `flow_version_id` (RESTRICT, pinned at create), `contact_ref`, `active_node_id` (React Flow node id inside the pinned flow, decides which agent runs each turn), `status` (`ChatbotSessionStatusEnum` active/inactive), `completion_status` (`ChatbotCompletionStatusEnum` in_progress/complete/abandoned), `collected_fields` (JSON flat `{field_name: value}`; `rag` sessions never populate it). No org/project columns, no agent-type column: tenant scoping joins through `chatbot`, and which agent runs is read from the pinned flow's active node type, not stored redundantly on the session. Indexes: `(chatbot_id, contact_ref)`, `contact_ref` (cross-chatbot latest lookup), partial unique `uq_chatbot_session_active_chatbot_contact` on `(chatbot_id, contact_ref) WHERE status = 'active'`.
- `chatbot_session_message` (`ChatbotSessionMessage`) — ordered transcript rows (`role` user/assistant), `node_id` = the flow node that handled the turn.
- Session lifecycle: one active session per contact + chatbot. `active`+`in_progress` → `active`+`complete` as fields are collected (onboarding only). Creating a new session for the same chatbot + `contact_ref` (same transaction as the insert) — or deleting the chatbot — moves active ones to `inactive`+`complete`, or `inactive`+`abandoned` if still in progress. Inactive sessions reject new messages (409); a turn already queued is skipped by the worker, which posts a failure webhook instead. A concurrent double-create hits the partial unique index; crud raises `ChatbotSessionConflictError` → 409.

## Flow JSON (Pydantic in `models/chatbot.py`)
- `ChatbotFlowNode` {id (1..255), type `ChatbotFlowNodeTypeEnum` (input/output/coordinator/onboarding/rag), position {x, y}, data}; agent nodes (`AGENT_NODE_TYPES`) validate `data` as `ChatbotAgentNodeData` {config_id: UUID?, config_version: int ≥ 1?, prompt?}. `ChatbotFlowEdge` {id, source, target, sourceHandle?, targetHandle?, data} — `data.intent` (required on coordinator edges at publish) / `data.description` (optional) drive coordinator routing. Extra keys allowed everywhere; dumped by alias.
- The first save goes live directly (validated + pinned like a publish); later draft saves validate shape only. Publish (`services/chatbot/flow.py:validate_flow_for_publish`) is strict: unique node ids; ≤ 1 input and ≤ 1 output node; edge endpoints exist; a flow-level check that the project has Anthropic credentials if it has any agent node; `_list_coordinator_problems`: ≤ 1 coordinator, ≥ 1 outgoing edge, every coordinator edge targets an onboarding or rag node (`COORDINATOR_TARGET_NODE_TYPES`), non-empty unique `data.intent` per coordinator; every agent node (`flow.py:SUPPORTED_AGENT_NODE_TYPES` = coordinator, onboarding, rag) has `config_id` + non-empty `prompt` and its config passes `get_chatbot_config_version` + `build_chatbot_model_settings`; a `rag` node additionally passes `prepare_rag_search_client` (non-empty, known `knowledge_base_ids` + OpenAI credentials); a null `config_version` is resolved to the latest and written back into the stored node; an entry node must resolve.
- Entry node (`resolve_entry_node`): no edges → the single agent node; otherwise the agent node targeted by the input node's only outgoing edge.

## Turn flow (onboarding node, `services/chatbot/agents/onboarding/graph.py`)
1. `extract_fields_node` — skipped until there is a real user turn (opening greeting). Otherwise calls the model with structured output (`FieldExtraction{collected_fields, missing_fields, missing_optional_fields, is_complete}`) over the node prompt, the previously collected map, and the (summarized) conversation. Uses Anthropic native structured output (`with_structured_output(..., method="json_schema")`) with the config's own thinking/effort, because forced tool use is rejected with thinking on and Opus 5.5 can't disable thinking. Merged in code: `{**prior, **extracted}`; `is_complete` only when no required field is missing; `is_done` = complete and no optional field (explicitly marked optional in the prompt) left unasked.
2. `chatbot_node` — replies using the same summarized view plus a system note listing collected/missing fields, so it asks only for what's missing, asks once for unasked optional fields when complete, and wraps up when done.
3. `run_chatbot_turn(..., collected_fields=prior)` → `ChatbotTurnResult{reply, collected_fields, is_complete, sources=[], is_done}` (`reply` = text of the graph's final `AIMessage` via `history.extract_final_reply`; empty → `ChatbotProviderError` `EmptyReply`) (`.completion_status` maps to the enum). Anthropic errors from either call, and langchain_anthropic's client-side model-config `ValueError`s ("[KAAPI] Unsupported model configuration"), map to `ChatbotProviderError` via the shared `provider_errors.to_provider_error`, so the session path always sends a failure webhook.

## Turn flow (rag node, `services/chatbot/agents/rag/graph.py`)
1. `prepare_context_node` — runs `summarize_if_needed` once and replaces the state messages (`RemoveMessage(REMOVE_ALL_MESSAGES)`), so the tool loop is never summarized mid tool_use/tool_result pair.
2. `agent_node` — chat model with `search_knowledge_base` bound (`tool_choice` auto; forced tool use is rejected with thinking). System prompt = `RAG_INSTRUCTION` + `<config_instructions>` (config `params.instructions`, if set) + `<goal>` (the node's `prompt`). After `MAX_TOOL_ROUNDS` (3) tool-calling AIMessages it is re-bound with `tool_choice={"type": "none"}` so it must answer.
3. `tools_condition` → `ToolNode` (`tools`) → back to `agent_node`; END once the model stops calling tools. Only bad tool args (`ToolInvocationError`) are fed back to the model; a search failure (`ChatbotProviderError`) fails the turn.
4. `search_knowledge_base(query)` (`retriever.py`, `content_and_artifact`) — `client.vector_stores.search` on every `knowledge_base_ids` entry (from the node's config), merged, sorted by score, top `max_num_results` (default 5, capped at 50); content is `<source file="...">text</source>` passages, artifact the `KnowledgeBasePassage` list. OpenAI errors → `ChatbotProviderError` (`[OPENAI] Knowledge base search failed ...`; timeouts/connection `[KAAPI]`).
5. `run_rag_turn(..., openai_client)` — rejects a missing `user_message` (`RAG_MESSAGE_REQUIRED_MESSAGE`; no kickoff greeting) → `ChatbotTurnResult{reply, collected_fields (unchanged), is_complete=False, sources}`; `sources` are the retrieved files deduped by `file_id`.

## Turn flow (coordinator, `services/chatbot/agents/coordinator/graph.py`)
- `run_coordinator_turn(..., routes, in_progress_intent=None)` → `CoordinatorDecision{target_node_id | clarifying_question}`. No LangGraph: one structured-output call (`RouteDecision{intent, clarifying_question}`, `method=EXTRACTION_METHOD`) over the coordinator prompt + enumerated intents + the full (summarized) transcript. Intent matched case-insensitively; with `in_progress_intent` set the prompt tells the model to keep that sub-flow and unmatched/null routes to it; otherwise unmatched/null → clarifying question (constant fallback if the model gave none). The opening turn (no user message) always clarifies.
- Worker dispatch (`services/chatbot/session.py`): an agent active behind a coordinator (`_find_return_coordinator`) is an in-progress sub-flow, so the turn still runs on the coordinator with `TurnContext.in_progress_node_id` set (its route's intent becomes `in_progress_intent`); flows without a coordinator run the active agent directly. The first DB session resolves the coordinator's settings and parses its routes + target nodes from the pinned flow (`_resolve_coordinator_routes`, no DB). After routing, only the chosen target's settings (and, for rag, knowledge-base validation + OpenAI client) load via `_resolve_node_runtime` in a second short DB session, so no connection is held across an LLM call. A broken target (deleted KB/config, removed credentials) fails only turns routed to it (failure webhook, no reply stored, `active_node_id` unchanged); clarify/greeting turns never load targets. Routed → the target agent replies in the same turn via `run_agent_turn` (silent handoff). Onboarding target: 3 sequential LLM calls (routing + extraction + reply); `active_node_id` → target, or back to the coordinator when the target's turn `is_done`. Rag target: routing + 1–4 rag calls; `active_node_id` unchanged (coordinator, or the in-progress onboarding node, so a FAQ mid-onboarding detours to rag without losing the sub-flow). Known gap: a long chat may be summarized twice (routing + agent). Clarify → coordinator replies, `active_node_id` unchanged.
- `completion_status` is per reply in coordinator flows: `complete` once an onboarding reply has every required field (the node may stay active asking optional fields), `in_progress` on rag replies and after the hand-back. `collected_fields` is one merged session-wide map, and every agent sees the whole transcript, including other sub-flows' answers.

## External
- Anthropic via `langchain-anthropic`, using the **project's own Anthropic credentials** (`services/chatbot/config.py:get_anthropic_api_key`; no platform `ANTHROPIC_API_KEY` fallback — missing credentials fail publish/first save with 422 and a turn with a failure webhook) — onboarding: two calls per turn once the user has spoken (extraction + reply); rag: one call per tool round (≤ 4); a coordinator turn adds one routing call before a handoff (so 3 on a turn routed to onboarding — including every message to an onboarding sub-flow already in progress, 1 + 1–4 on a turn routed to rag, 1 on a clarify turn); plus one summary call when history exceeds the token budget.
- OpenAI vector store search (`vector_stores.search`, rag only) with the project's OpenAI credentials, one call per knowledge base per tool call; `OPENAI_TIMEOUT_SECONDS`, one SDK retry.
- Caller webhook (`send_callback`, HMAC-signed with the project webhook secret).
- kaapi-frontend React Flow editor reads/writes the flow JSON as-is.
