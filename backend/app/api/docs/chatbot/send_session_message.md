Queue one turn of a chatbot session; the bot reply is delivered asynchronously to `webhook_url`.

The user `message` is stored immediately (tagged with the session's active node) and the response is `202` with `status: "queued"`. Once the turn completes, Kaapi POSTs `{"success": true, "data": {"session_id", "chatbot_id", "node_id", "reply", "status", "completion_status", "collected_fields", "sources"}}` to `webhook_url` (HMAC-signed when the project has a webhook secret). On a model, config, or knowledge-base search failure it POSTs `{"success": false, "error": "...", "data": {"session_id"}}` instead.

The turn runs the session's active node of its pinned flow version (in a coordinator flow, the coordinator first; see below): the node's `data.prompt` is the system prompt and its `data.config_id` / `data.config_version` supply the model. For an `onboarding` node, each turn re-reads the conversation against that prompt and saves every field the user has given into `collected_fields`, a flat `{field_name: value}` map with snake_case keys (values are only ever taken from what the user said; a correction overwrites the old value). `completion_status` is `complete` once every required field is collected and `in_progress` otherwise; it is computed from a structured extraction, not from the reply text. A `complete` session still accepts messages. For a `rag` node, the bot searches the config's knowledge bases when the question may be covered by them and answers from the retrieved passages; `collected_fields` is left unchanged and `completion_status` stays `in_progress`. `sources` lists the documents retrieved for the turn as `[{"file_id", "filename"}]`, deduplicated by `file_id` (always `[]` for `onboarding`, and for `rag` turns that didn't search). `status` (`active`/`inactive`) is separate and says whether the session is in use: once a newer session is created for the same contact and chatbot, or the chatbot is deleted, this one is `inactive` and rejects new messages with 409. A turn that was already queued when that happened is not run; Kaapi POSTs the failure payload with error `[KAAPI] Chatbot session was superseded by a newer session; start a new session.` instead.

In a flow with a `coordinator`, the coordinator classifies every message against its outgoing edges' intents, including messages sent while one of its `onboarding` targets is active; it defaults to that in-progress sub-flow unless the user clearly asks for something another intent covers. On a match the target node writes the reply in the same turn (one webhook); `node_id` in the webhook is the node that produced the reply (`sources` is non-empty only on `rag` replies). A `rag` reply never changes the active node. A routed `onboarding` node stays active until every required field is collected and any optional fields its prompt lists have been asked for once (given or declined); then the session returns to the coordinator. So `completion_status: complete` (required fields collected) can arrive while the `onboarding` node is still active and asking optional fields — do not read `complete` as "control returned to the coordinator". A `rag` reply in between reports `in_progress`. If nothing matches and no sub-flow is in progress, the coordinator replies with a clarifying question and the session stays on it; the opening greeting is always the coordinator's own. `collected_fields` is one map shared by every agent in the session.

For an `onboarding` or `coordinator` entry node, omit `message` on the first call of a session to get the bot's opening greeting; after that `message` is required. A `rag` node has no opening greeting — it only answers what the user asks — so `message` is required on every call, including the first. `webhook_url` must be a public HTTPS URL. Returns 404 if the session isn't in the caller's project, 409 if the session is inactive, and 422 for an invalid `webhook_url`, a missing `message` on a started session, or a missing `message` on a `rag` node.
